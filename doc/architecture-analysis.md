# 景区导览AI数字人 — 架构分析文档

> 本文档基于赛题要求（A5-景区导览服务AI数字人）与团队现状的架构咨询记录整理。

## 一、项目概况

| 维度 | 内容 |
|------|------|
| 赛题 | 第十五届中国软件杯 A组 A5 — 景区导览服务AI数字人 |
| 出题企业 | 锐捷网络（苏州）有限公司 |

## 二、已确认的架构决策

### 2.1 技术栈选型

| 层级 | 技术 | 说明 |
|------|------|------|
| 前端 | Vue3 | 游客交互端 + 管理后台 |
| 后端 | FastAPI | 游客端业务API + 数据抓取 + 统计聚合 + 大屏API |
| 数字人 | light4ai (iframe嵌入) | 已配置TTS、ASR、Dify Chat Agent对接 |
| 智能体 | Dify (Docker部署) | Chat Agent + 景区知识库（已上传）+ 量化评估工作流 |
| 模型 | API调用（非本地推理） | 不跑模型，通过API服务 |
| 数据库 | 待定 (SQLite / PostgreSQL) | 单人开发建议SQLite起步 |

### 2.2 核心架构决策：FastAPI为业务中枢 + iframe接入数字人

**决策**：FastAPI作为前后端业务中枢，同时服务游客端和管理后台；游客端的数字人交互部分通过iframe嵌入light4ai，后端通过Dify API旁路抓取对话数据做统计分析。

**关键关系**：
- Vue3游客端 → FastAPI：业务请求（页面数据、个性化推荐、路线信息、景点介绍等）
- Vue3游客端 → light4ai(iframe)：仅数字人对话交互
- Vue3管理后台 → FastAPI：统计查询、报告数据
- light4ai → Dify：对话处理（Chat Agent + 知识库）
- FastAPI → Dify：旁路抓取对话 + 调用量化工作流

**数据流链路**：
```
游客端Vue3 ──业务请求──→ FastAPI（推荐/路线/景点数据）
    │
    └──iframe──→ light4ai数字人 → Dify Chat Agent回答
                                    ↓ (旁路)
                          FastAPI抓取对话 → 调用Dify量化工作流 → 评分入库
                          
管理后台Vue3 ──查询──→ FastAPI ──→ 数据库 → 大屏/报告展示
```

### 2.3 功能取舍

赛题要求管理后台4项功能，单人开发做如下取舍：

| 功能 | 决策 | 理由 |
|------|------|------|
| 数据大屏概览 | ✅ 自研 | 评分权重高，展示效果好 |
| 游客感受度报告 | ✅ 自研 | 赛题核心差异化能力 |
| 知识库管理 | ⏭️ 用Dify原生 | Dify已有完整知识库管理，无需重复造轮子 |
| 数字人形象管理 | ⏭️ 用light4ai配置 | light4ai后台已支持形象配置 |

### 2.4 量化评估指标

在Dify上搭建量化评估工作流，对每段对话产出结构化评分：

| 指标维度 | 输出 | 用途 |
|----------|------|------|
| 运营数据统计 | 问题分类、访问量、热门TOP | 数据大屏 |
| 情感/满意度分析 | 情感标签 + 满意度评分(1-5) | 感受度报告 |
| 关注点/建议 | 高频关注点、投诉点、改进建议 | 感受度报告 |
| 景点维度分析 | 提及景点、各景点问答分布 | 运营辅助 |

## 三、关键技术风险

### 风险1：对话数据抓取的实时性 ⚠️

**问题**：Dify Chat Agent默认不主动推送对话事件，FastAPI如何拿到对话数据？

**候选方案**：
- **方案A（推荐）**：FastAPI定时轮询Dify的 `GET /conversations/{id}/messages` API，拉取新增对话
- **方案B**：将Chat Agent改为Workflow，在末尾加HTTP请求节点，对话结束后回调FastAPI
- **方案C**：用Dify的Webhook能力（如果版本支持）

**权衡**：方案A最简单但有延迟；方案B实时性最好但需要改造现有Chat Agent；方案C依赖Dify版本。

### 风险2：量化工作流的调用成本 ⚠️

**问题**：每次对话都要调一次量化工作流（本质是再调一次LLM），API成本翻倍。

**建议**：批量处理 —— FastAPI积累N条对话后批量调用工作流，或用定时任务每5分钟处理一批。

### 风险3：iframe跨域限制 ⚠️

**问题**：Vue3主页面向iframe内的light4ai发消息/接收消息受同源策略限制。

**现状**：已通过`allow="microphone"`解决麦克风权限。但主页面向iframe传参（如游客ID、会话上下文）需要用`postMessage`，且light4ai需支持接收 —— **这一点未确认**。

### 风险4：响应延迟 < 5秒

**问题**：赛题要求语音问答延迟<5秒。链路是 ASR→Dify→TTS→渲染，任一环节卡顿都会超时。

**建议**：Dify Chat Agent确保用流式输出（streaming）；知识库检索优化chunk大小。

## 四、已确认的决策

| # | 问题 | 决策 | 理由 |
|---|------|------|------|
| Q1 | 对话数据抓取 | **轮询Dify API**（每30秒） | 不动Chat Agent，简单可靠，30秒延迟可接受 |
| Q2 | 量化触发时机 | **批量定时**（每5分钟） | 平衡API成本和实时性 |
| Q3 | 个性化推荐 | **暂不确定，搁置** | 推荐数据已有基础，但实现方式待定 |
| Q4 | 景区信息 | **Dify知识库纯文档，已测准确率，有景点×年龄段推荐数据** | 见下方详细说明 |
| Q5 | 游客身份 | **localStorage生成游客ID** | 零摩擦，可关联同设备多次访问 |
| Q6 | 部署形态 | **混合部署：Dify服务器端 + 前后端本地** | 服务器资源不足，本地跑展示 |
| Q7 | 数据库 | **SQLite + SQLAlchemy ORM** | 零运维，后续可无缝迁移PostgreSQL |

## 五、景区信息与推荐数据说明

### 知识库现状
- **内容**：纯文档资料（无图片），已上传Dify知识库
- **准确率**：已测试，问答准确率达标
- **推荐数据**：知识库中包含「每个景点对不同年龄段游客的推荐程度」结构化数据

### 推荐数据的价值
知识库中已有的「景点×年龄段→推荐程度」数据是个性化推荐的天然基础：
- 如果后续做Q3个性化推荐，FastAPI可直接从Dify拉取或本地缓存这份推荐矩阵
- 游客选择年龄段/兴趣标签后，FastAPI查推荐矩阵返回匹配路线
- **实现成本不高** —— 数据已有，只需写查询接口和前端展示

### 量化工作流景点维度分析
由于知识库中有景点相关结构化数据，量化评估工作流在做"景点维度分析"时可以：
- 从对话中提取提及的景点名称
- 关联景点的年龄段推荐属性
- 统计各景点的问答频次、满意度分布

### 混合部署的影响
| 维度 | 影响 | 应对 |
|------|------|------|
| 轮询延迟 | FastAPI远程调Dify API，网络延迟叠加30秒轮询 | 可接受，统计场景不要求实时 |
| 演示稳定性 | 依赖服务器端Dify可用性 | 演示前确认Dify服务正常 |
| 部署文档 | 需说明本地+远程的混合配置 | 文档中明确标注各服务地址 |
| 评委验证 | 评委本地跑需配Dify地址 | 提供.env配置文件，填入Dify API地址即可 |
- 有云服务器的话额外提供演示地址

**如果没有异议，按此方案执行。**

## 六、架构决策记录

### ADR-001: FastAPI作为业务中枢 + iframe接入数字人

**Status**: Accepted

**Context**: 需要在单人开发约束下，同时满足"数字人多模态交互"和"后台数据统计"两个核心需求，且游客端需要业务功能（推荐、路线、景点介绍等）。自建开源数字人项目运维成本高，纯iframe又拿不到数据。

**Decision**: FastAPI作为业务中枢，同时服务游客端和管理后台。游客端的数字人交互部分通过iframe嵌入light4ai（已配置TTS/ASR/Dify对接），其余业务功能（页面数据、个性化推荐、路线信息等）由FastAPI直接提供API。后端FastAPI通过Dify API旁路抓取对话数据，调用Dify量化工作流分析后入库。

**Consequences**:
- ✅ 开发量小，数字人交互部分几乎零开发
- ✅ FastAPI统一管理所有业务API，职责清晰
- ✅ 游客端的业务功能和数字人对话解耦，互不影响
- ✅ 数据统计功能可独立于数字人前端演进
- ✅ light4ai负责口型/表情/TTS/ASR，减少自研负担
- ⚠️ 依赖light4ai第三方服务稳定性
- ⚠️ iframe跨域限制导致主页面与数字人交互受限
- ⚠️ 对话数据抓取有延迟（取决于方案选择）

### ADR-002: 管理后台聚焦数据大屏 + 感受度报告

**Status**: Accepted

**Context**: 赛题要求4项后台功能，但单人开发精力有限。

**Decision**: 自研数据大屏和感受度报告；知识库管理用Dify原生能力；形象管理用light4ai配置。

**Consequences**:
- ✅ 聚焦评分权重高的部分
- ✅ 避免重复造轮子
- ⚠️ 评委可能认为功能不完整 —— 需在文档中说明设计理由

### ADR-003: 量化评估走Dify工作流

**Status**: Proposed

**Context**: 需要对每段对话产出情感、满意度、关注点、景点维度等结构化评分。

**Decision**: 在Dify上搭建量化评估工作流，输入对话内容，输出结构化JSON评分，由FastAPI调用并存入数据库。

**Consequences**:
- ✅ 复用Dify的LLM编排能力，无需FastAPI侧写复杂prompt
- ✅ 工作流可视化，便于调优
- ⚠️ 每次对话多一次LLM调用，API成本翻倍
- ⚠️ 需设计批量处理机制控制成本

### ADR-004: 回退超前实现功能，回归设计原貌

**Status**: Accepted

**Context**: 2026-07-12 状态审视发现，实际代码比设计文档超前实现了三项功能：
1. 个性化推荐（Q3 原决策为「搁置」）
2. 景区数据本地同步（scenic_spots 表 + scenic_sync 定时任务）
3. 景点维度分析（P2 加分项）

超前实现带出了未验证的假设（Dify `/documents` 返回 content 字段、iframe 透传 visitor_id）、过频的轮询（5分钟同步静态数据）、以及对 ScenicSpot 表的连锁依赖。在单人开发、赛题硬性指标未稳的前提下，这些「加分项」反而稀释了对核心链路（对话抓取→量化→大屏）的验证精力。

**Decision**: 删除上述三项超前实现功能及其连锁代码，回归设计文档原貌。具体删除：
- 后端：`scenic_spot` 模型、`scenic_sync` service/task、`recommend_spots`、`get_spot_detail`、`get_spot_analysis`、dify_client 的 datasets 方法、dialogue/analysis 占位 API 保留待处理
- 前端：`RecommendView.vue`、`SpotDetailView.vue`、`SpotAnalysisView.vue`、`useFormatAgeRec.ts` 及对应路由和导航

**Consequences**:
- ✅ 架构与设计文档严格对齐，文档分（10分）更容易拿满
- ✅ 消除 scenic_sync 带来的 3 个技术债（D/E/F，见 status-review.md）
- ✅ 精力聚焦核心链路：数字人对话 → 轮询抓取 → 量化分析 → 数据大屏/感受度报告
- ✅ 游客端业务功能简化为「首页 + 数字人对话」，景点介绍回归 Dify 知识库对话方式
- ⚠️ 丧失个性化推荐的差异化加分，但原设计本就搁置此功能
- ⚠️ 丧失景点维度分析看板，但数据大屏的 `spot_heatmap` 仍保留（统计对话中提及的景点，不依赖本地景点表）
- 🔁 可逆：若核心链路稳定后有余力，可重新实现推荐功能（数据基础仍在 Dify 知识库）
