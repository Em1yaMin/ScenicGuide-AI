# 架构决策问题清单 — 详细方案对比

> 每个问题给出背景、可选方案、利弊权衡和推荐方向。请逐个确认。

## Q1: 对话数据抓取方案 ⭐最关键

### 背景
游客通过iframe与数字人对话，对话在 `light4ai → Dify` 链路中完成。FastAPI需要拿到这些对话内容才能做量化分析。问题是：**FastAPI怎么拿到Dify里的对话数据？**

### 方案A：FastAPI定时轮询Dify API（推荐）

**做法**：FastAPI起一个定时任务（如每30秒），调用Dify的 `GET /conversations/{conversation_id}/messages` 接口，拉取新增对话消息，去重后入库。

```
FastAPI定时任务(每30s) → 调Dify API拉取messages → 去重 → 入库
```

| 维度 | 评价 |
|------|------|
| 实现难度 | 低 — Dify API原生支持，Python写个定时任务即可 |
| 实时性 | 有30秒~1分钟延迟，但对统计场景完全够用 |
| 对现有Agent | 零改造 — Chat Agent不动 |
| 可靠性 | 高 — 拉取失败可重试，不丢数据 |
| 风险 | 需要维护conversation_id列表；Dify API限流要注意 |

### 方案B：改造Chat Agent为Workflow + HTTP回调

**做法**：把Dify的Chat Agent改造成Workflow模式，在Workflow末尾加一个HTTP请求节点，对话结束后自动回调FastAPI的接口推送对话数据。

```
Dify Workflow结束 → HTTP请求节点 → POST FastAPI /api/dialogue → 入库
```

| 维度 | 评价 |
|------|------|
| 实现难度 | 中高 — 需要改造现有Chat Agent，Workflow配置比Chat Agent复杂 |
| 实时性 | 极好 — 对话结束立即推送，零延迟 |
| 对现有Agent | 需改造 — Chat Agent→Workflow，要重新调试知识库检索效果 |
| 可靠性 | 中 — 回调失败需设计重试机制 |
| 风险 | Workflow模式的知识库检索效果可能与Chat Agent有差异，要重新验证准确率 |

### 方案C：Dify Webhook/事件订阅

**做法**：如果Dify版本支持Webhook或事件订阅功能，配置对话完成事件回调FastAPI。

| 维度 | 评价 |
|------|------|
| 实现难度 | 低（如果支持的话） |
| 风险 | **依赖Dify版本和功能支持**，需先确认你的Dify版本是否有这个能力 |

### 📌 推荐：方案A
单人开发优先简单可靠。30秒延迟对"后台统计"场景完全可接受（又不是实时翻译）。Chat Agent不用动，知识库准确率不用重新验证。后续有余力再升级到方案B。

## Q2: 量化工作流触发时机

### 背景
拿到对话数据后，要调用Dify量化工作流分析（情感、满意度、关注点、景点维度）。**每调一次量化工作流 = 再调一次LLM API = 多花一份钱。** 所以要决定什么时候触发分析。

### 方案A：每条对话实时分析

**做法**：FastAPI抓到一条对话，立即调一次量化工作流。

| 维度 | 评价 |
|------|------|
| 实时性 | 极好 — 管理后台随时看到最新分析 |
| 成本 | 高 — 对话1次LLM + 分析1次LLM = 成本翻倍 |
| 适用场景 | 对话量小（每天<100条）时成本可控 |

### 方案B：批量定时分析（推荐）

**做法**：FastAPI积累对话，每5分钟批量处理一次。可一次分析多条，或逐条分析但集中触发。

| 维度 | 评价 |
|------|------|
| 实时性 | 有5分钟延迟，大屏数据准实时 |
| 成本 | 可控 — 可以合并多条对话一起分析减少调用次数 |
| 适用场景 | 通用，平衡成本和实时性 |

### 方案C：按需分析

**做法**：不主动分析，管理后台请求报告时才触发。

| 维度 | 评价 |
|------|------|
| 实时性 | 差 — 报告生成慢，无法做实时大屏 |
| 成本 | 最低 — 只在需要时算 |
| 风险 | 评委看大屏时如果数据没预计算，体验差 |

### 📌 推荐：方案B
每5分钟批量分析一次。如果实际对话量不大（比赛演示场景），方案A也可以接受。关键是**不要让评委看大屏时发现数据没算好**。

## Q3: 个性化推荐实现方式

### 背景
赛题要求"根据游客兴趣推荐不同游览路线和讲解重点"。当前数字人是iframe嵌入的，FastAPI是业务中枢。**推荐功能放哪实现？**

### 方案A：Vue3独立推荐模块（推荐）

**做法**：游客端页面加推荐入口，用户选兴趣标签（历史/自然/亲子等），调FastAPI拿结构化推荐路线，页面展示。

| 维度 | 评价 |
|------|------|
| 可控性 | 高 — 推荐逻辑在FastAPI，路线数据结构化存储 |
| 体验 | 中 — 推荐和数字人对话是两个独立操作 |
| 实现 | 简单 — FastAPI查数据库返回路线即可 |

### 方案B：Dify Chat Agent prompt加推荐能力

**做法**：在Chat Agent的system prompt里加推荐指令，游客对话中说"我对历史感兴趣"，数字人直接口播推荐路线。

| 维度 | 评价 |
|------|------|
| 可控性 | 低 — 推荐依赖LLM理解，可能不准 |
| 体验 | 好 — 对话式推荐，自然 |
| 实现 | 简单 — 改prompt即可，但路线数据要进知识库 |

### 方案C：两者结合

**做法**：数字人对话识别兴趣 → 但推荐路线走FastAPI结构化返回 → 页面展示 + 数字人口播。

| 维度 | 评价 |
|------|------|
| 体验 | 最好 — 对话+可视化路线 |
| 实现 | 复杂 — iframe跨域限制，数字人可能拿不到FastAPI数据 |

### 📌 推荐：方案A为主 + 方案B为辅
Vue3独立推荐模块做结构化展示（保证准确），同时在Chat Agent的prompt里加一句"如果游客问路线，可以推荐"（对话式补充）。不追求方案C的深度集成。

## Q4: 景区资料包具体信息 ⭐需补充

### 背景
赛题提供示范景区资料包，已下载并上传到Dify知识库。但以下信息直接影响知识库检索效果和景点维度分析，**需要你补充说明**：

### 需要确认的信息

1. **是哪个景区？**
   - 景区名称、规模、主要景点数量
   
2. **资料包内容结构？**
   - 文档类型（PDF/Word/TXT/图片？）
   - 内容分类（历史介绍？景点说明？路线图？FAQ？门票信息？）
   - 数据量（多少份文档？大约多少字？）
   
3. **Dify知识库现状？**
   - 上传时有没有分块处理？
   - 用的是什么检索模式（向量检索/全文检索/混合）？
   - 有没有测试过问答准确率？
   
4. **是否已整理结构化数据？**
   - 景点列表（名称+简介+位置）
   - 推荐路线（如：历史线2小时/亲子线3小时）
   - 常见FAQ清单

### 为什么重要
- 景点维度分析需要知道有哪些景点 → 没有景点列表就没法做"各景点问答分布"
- 知识库检索准确率≥90%是硬指标 → 需要知道当前检索效果如何
- 个性化推荐需要路线数据 → 没有结构化路线就没法推荐

## Q5: 游客身份与会话关联

### 背景
需要区分不同游客的对话，统计"游客A问了什么""同一游客多次访问的满意度趋势"等。**怎么标识游客？**

### 方案A：完全匿名，用Dify conversation_id

**做法**：Dify每次对话会生成conversation_id，直接用它做游客标识。

| 维度 | 评价 |
|------|------|
| 实现 | 零成本 — 不用写任何代码 |
| 关联能力 | 弱 — 同一游客每次新会话就是新ID，无法关联多次访问 |
| 适用场景 | 只统计总量，不关心个体 |

### 方案B：localStorage生成游客ID（推荐）

**做法**：Vue3前端首次访问时生成一个UUID存localStorage，后续所有请求（包括传给数字人的会话）都带这个ID。

| 维度 | 评价 |
|------|------|
| 实现 | 简单 — 前端几行代码 |
| 关联能力 | 中 — 同一设备多次访问可关联，清缓存/换设备失效 |
| 游客体验 | 零摩擦 — 无需登录 |
| 适用场景 | 景区场景最合适，游客不会为了导览登录 |

### 方案C：简单登录（可选填昵称/手机号）

**做法**：游客可选填昵称或手机号关联身份。

| 维度 | 评价 |
|------|------|
| 实现 | 中等 — 需要登录页面和接口 |
| 关联能力 | 强 — 精准关联 |
| 游客体验 | 差 — 景区场景没人愿意填手机号用导览 |

### 📌 推荐：方案B
localStorage生成游客ID，配合Dify conversation_id做会话级标识。零摩擦且能关联同设备多次访问，最适合景区场景。

## Q6: 部署形态

### 背景
最终交付物需要可部署运行，评委可能需要自行部署验证。**怎么打包交付？**

### 方案A：Docker Compose一键部署（推荐）

**做法**：FastAPI + 前端(nginx) + 数据库 打包成docker-compose，Dify单独部署（已有）。提供 `docker-compose up` 一键启动。

| 维度 | 评价 |
|------|------|
| 评委体验 | 好 — 一键跑起来 |
| 专业度 | 加分 — 体现工程能力 |
| 实现成本 | 中 — 需要写Dockerfile和compose配置，但单人也能搞定 |

### 方案B：手动部署 + 文档

**做法**：提供详细部署文档，手动启动各服务。

| 维度 | 评价 |
|------|------|
| 评委体验 | 差 — 容易出错 |
| 专业度 | 一般 |
| 实现成本 | 低 |

### 方案C：云端演示 + 本地部署文档

**做法**：提供云端可访问的演示地址 + 本地部署文档/Docker。

| 维度 | 评价 |
|------|------|
| 评委体验 | 最好 — 直接看演示 |
| 成本 | 需要云服务器持续运行 |
| 风险 | 演示期间服务要稳定 |

### 📌 推荐：方案A + 方案C（如果有云服务器）
Docker Compose是底线，有云服务器的话额外提供演示地址加分。单人也建议做Docker Compose，不复杂但专业度提升明显。

## Q7: 数据库选型

### 背景
需要存储对话记录、量化指标、聚合统计数据。**用什么数据库？**

### 方案A：SQLite（推荐）

**做法**：直接用SQLite，文件型数据库，Python原生支持，零配置。

| 维度 | 评价 |
|------|------|
| 运维 | 零 — 不用装数据库服务 |
| 开发速度 | 快 — Python sqlite3模块直接用 |
| 性能 | 够用 — 单人比赛项目并发量极低 |
| 功能 | 基础SQL够用，JSON存储可用TEXT字段存 |
| 迁移性 | 好 — 后续可无缝迁移到PostgreSQL（SQL语法兼容） |

### 方案B：PostgreSQL

**做法**：部署PostgreSQL，用JSONB字段存量化分析结果。

| 维度 | 评价 |
|------|------|
| 运维 | 需额外部署 — Docker里加一个pg容器 |
| 开发速度 | 中 — 需要配置连接、建表 |
| 性能 | 强 — 但比赛场景用不到 |
| 功能 | JSONB字段存量化结果方便查询 |
| 专业度 | 加分 |

### 方案C：SQLite开发 + PostgreSQL生产

**做法**：开发用SQLite，Docker部署用PostgreSQL。

| 维度 | 评价 |
|------|------|
| 灵活性 | 开发快 + 部署专业 |
| 风险 | 两套环境可能有兼容性问题（如JSON字段处理差异） |

### 📌 推荐：方案A
单人比赛项目SQLite完全够用，把精力放在功能实现上。用SQLAlchemy做ORM，后续要迁移PostgreSQL只需改连接字符串。如果评委问，回答"架构支持无缝迁移"。
